# 从来源到本地模板包

使用 [v0.4 编审语法](../../../../docs/template-library-v04.md)。编审容器仍为 `schema_version: 3`，每组用 `syntax_version: "0.4"`、`extra_key`、新版条件和带稳定 ID 的话术对象。场景采用新版根对象与具名动作字段，旧 `argN` 输入供回放验证。

## 输入与证据

每次生成先取得用户命名的本地 JSON 路径，已有文件名直接使用。未给出则询问；单纯审阅现有材料不触发生成。工作稿、场景和评语存入 raw 下本次工作目录，交付文件只含 v3 规定的内容。输出路径若已有同名文件，核实是用户指定更新的那份，再替换。

- 笔记按[知识契约](../../wanxiangqi-knowledge/references/knowledge-contract.md)读取。已有文字稿以可回查的段落或时间定位。
- 输入搜索主题时，先查本地来源索引与全文。需要 B 站搜索时在项目根目录执行 `.wxq-runtime/Scripts/python.exe -X utf8 .codex/skills/wanxiangqi-template/scripts/search_videos.py "搜索主题"`（后续页用 `--page`），复用项目现有 B 站检索器；核对标题、作者、BV、分 P 与教学主题。直接给链接时从对应 BV 和分 P 开始。
- 复用[知识采集流程](../../wanxiangqi-knowledge/references/workflow.md)。有完整对应的文字稿直接读；否则使用项目 Python 执行 .codex/skills/wanxiangqi-knowledge/scripts/wxq.py prepare 视频链接。优先中文字幕，无有效字幕时使用 large-v3。检查完成状态并逐段核对转写。原始 ASR 原样保留，修正版和纠错记录保留时间、原词、标准词、对应实体及判断依据。结合官方卡面、上下文和必要画面判断；未辨明的内容留作疑点。来源抓取失败时报告失败的 BV、分 P 和阶段。只生成模板文件时不触发知识提案或沉淀。

给 Gemini 整理知识摘要时，也要校对措辞。卡面名称、技能名和机制术语按来源核实。其余内容用完整、自然的中文交代谁做了什么、发生了什么变化。编辑笔记里的临时简称、抽象概括和 ASR 疑词不能直接写进题面。摘要只提供事实、范围、来源和决策方向。定向评测应在封存题面前完成这项检查；封存后发现的题面问题写进评审，跨轮比较时保留同一份输入。

## 选择事件与骨架

先从独立知识还原玩家的选择和收益，确定事件，再查[事件索引](event-angles.md)。叠加共用标准、事件标准与策略，逐条核对该事件「骨架库」中的条件。括号里的阵容需求、特殊功能、时机等都必须有来源和局面支持。案例帮助理解已确认骨架，不能开辟新骨架。

- 按[每个事件先通用后具体](../SKILL.md#4-每个事件先通用后具体)完成骨架覆盖核对。先为有据的通用理由建组或确认可复用的已有组，再检查专门条件能否增加一项独立的取舍。
- 有适用骨架才建组。已有库但没有命中时记录来源、检查过的编号和缺失条件，跳过。禁止借邻近事件骨架建组、泛化骨架以强行匹配。
- 用户明确暂停的事件直接记录跳过，不重复询问草案。其余空库先参考其他事件，提交草案，分别说明参考编号、为何可迁移、触发条件与话术方向。等用户明确确认具体条目，再赋稳定编号收入该事件「骨架库」。草案、评测批次和已确认条目分开；未确认前停止该事件的候选生成。
- 三组举一反三事件为购买／选择／首拍／二拍英雄（E01、E06、E07）、购买／选择／第三次拍卖效果牌（E11、E10、E12），以及穿戴／铸造／转移装备（E13、E14、E15）。先核对卡牌阶级与各途径的候选规则。第三次拍卖只覆盖 6 阶效果牌，1 至 5 阶继续配齐交易和选择。对每层理由在所有可发生的事件配组，核对可观察的前提、对象范围与收益。共用条件按同一顺序书写，将正式动作路径和键换成该事件对应的映射。可发生的事件缺少可观察前提或已确认骨架时，记录原因并暂缓整个共享层。动作独有理由可单列，注明机制和证据。

## 逐段覆盖记录

关联组的 `related_events` 继续按事件文档编号记录骨架判断。每个启用的关联组另填 `sync`。共享组填写 `reason` 和 `tier`，跨事件使用相同值。独有组填写 `exclusive` 和 `evidence`。构建器按正式卡面核对已点名的效果牌阶级。用通配键表达同阶卡牌时，填写有依据的 `effect_card_tier`（整数 1 至 6），并核验条件能限定该范围。一轮英雄拍卖实际无法取得对象时，在同一共享层各组填写 `unavailable`，以正式事件为键，以该轮的规则和证据为值。构建器按实际成品核对共享层的事件、动作键与生效条件。

从输入先独立列出 `inventory`（段落、条目、表格单元格或文字稿片段定位），再逐项填 `units`。每项用 `source` 对应清单，`materials` 列出全部可用素材。没有素材时写空数组并填写 `reason`。

- 素材写 `decision` 和 `events`。每个事件用正式 `event` 名称，按前提从少到多列 `checks`。每项使用 `skeleton`、`status` 和具体 `reason`。空库或未登记的事件用空 `checks` 并注明 `reason`。
- 建组或复用时用 `status: "group"` 和 `group: [正式事件名, 稳定组 ID]`。共用组可从多个素材引用。需要通用组的细分记录同时填写 `bases`，其元素是同样格式的组定位，通用组须先登记。跳过用 `status: "skip"`，写明证据、可观测性或新增收益缺在哪里。
- 对照输入复点清单。逐项反查实际发出的模板和求值场景，确保覆盖范围、优先级、去掉细分前提后的基础播报和素材处置都经复核。

## 撰写、复核与交付

条件复核先于构思。逐项记录动作、键和范围已经保证的事实、每项条件保留或删除的理由及反例。只用于证明动作值得做、且不改变解释的话术前提应删除。例如选择无限进步后，曹操是否在场与容错不影响天赋结算。分讲经验与满级能量时才需用等级区分。

按技能正文的阶段限制和双向匹配规则定稿条件。构思请求提供每个分支可观察的事实、这些事实如何改变收益，以及阶段词和具体阈值的对应关系。筛选首批候选时逐句重做对应检查：任一分支无法证明句中断言，或额外条件对该句没有作用，都淘汰。阶段上限取正式阶段枚举或有依据的回合边界；没有可验证边界时只讲有证据的当下收益。

由 Gemini 先按技能正文的五个标题生成 `wording_brief`。检查自然语言条件覆盖全部分支、能独立交给其他模型使用、示例可播。另发首批 16 句请求，传入通过复核的构思原文。首批构思与候选的请求、响应、复核分别归档。候选先判定 `qualified` 和理由，再以 `accepted` 标明是否选入，记录综合质量和有实质差异的依据。最多 3 条最佳句和 3 条差异句，保留首批原句和相对顺序。

刷新保留已通过现行标准的原句和人工作品。只需沿同一共享理由复用话术时，逐事件核对原句是否适用于自己的动作，再记录原句来源和复用范围。新增措辞按下文走首批生成和筛选。

逐组使用[项目 Gemini 撰写工具](../../wanxiangqi-knowledge/references/gemini-generation.md)发出请求。构思请求提供已核实的知识、正式事件与条件、已选骨架、正式术语和[用词辨析](banned-terms.md)。候选请求在 `context.话术构思` 传入已保存到 `wording_brief` 的构思原文。保存请求和无反馈的首批成功响应，记录失败情况。

发出首稿请求前，先把组请求保存为草稿，再用以下命令将当轮的 [writing-strategy.md](writing-strategy.md) 全文注入 `context.完整写作策略`。发送这份包含共用策略和完整词表的实际请求给 Gemini，并与首批响应一起归档。盲测每题同样在首稿前注入当轮冻结的全文。

```powershell
.wxq-runtime/Scripts/python.exe -X utf8 .codex/skills/wanxiangqi-template/scripts/wording.py raw/reports/请求草稿.json raw/reports/实际请求.json
```

Codex 对每句分别核对事实与措辞。逐项识别动词实际作用的对象，将正式名称、数字、语序和限定语还原到词表中的组合。任何涉及表内对象却未获批准的动宾搭配，或命中禁用表达的候选，均写明原词和对象后淘汰。先问事件、条件、受益者和局面价值是否准确，再遮住解释朗读：玩家会不会这样说，动词和宾语搭配是否自然，能否一听就知道谁做了什么。记下具体好坏词组，任何一项未过都淘汰。禁止生造词。意思不清、出现错词、主谓搭配生硬、超长或与其他已选句重复的候选均淘汰，保留具体原因。剩余的全部原样入组。每题只做这一批，不反馈重写、不补句、不手改。没有合格句就登记该题为 0 句；其他题继续交付。相邻比较只作可选写作参考，不影响单句取舍。每个新的独立评测轮次重新发出当轮题面和当轮通用标准，每题仍只生成一次。

说明沿用现有三个字段。explanation_before 保留原始知识、推导、自然语言条件、表达式及简短播报取舍，逐个列出本组实际采用的骨架编号和命中证据，并解释括号中的判断；explanation_source 只列来源定位；explanation_after 写实际求值、逐句复核和竞争组检查结论。

使用 scripts/build_local.py 包工作稿.json 复核记录.json 场景.json 用户指定文件.json --coverage 覆盖记录.json 做最终本地校验与写出。包内提供 events 数组（全为已登记事件可以为空），生成器写文件前通过项目正式 v3 解码与只读内存预演，核实棋手、阵容和参数身份。包内使用正式 condition_catalog（只读获取），每组提供正例、单项反例、缺值与能实际胜出的局面。名称和数字槽位需有展开预期。复核记录是数组，每项以 event_name、group_id 定位，另填 name 供阅读，gemini_request 和 gemini_state 是相对复核记录文件的请求与成功状态路径。写出前核对覆盖、话术构思原文、请求指纹、16 句原文与顺序，仅接受首批原稿。attempt 固定为 1，skeletons 为采用的编号列表，candidates 为按原序的 16 个对象。每项用 text、accepted（布尔）、verdict（逐句理由），可选填 improvement 和 improved 记录相邻比较，允许没有改善或省略。关联组三项检查以 related_events 对象保存，用三个事件编号作键，各值记录独立判断与依据。关联检查和失败批次留在本次工作目录，禁止将候选审计字段塞入模板包。只有用户另行要求入库时才走正式导入流程。

写出时用正式事件动作代入键中已确定的参数作为组名。例如 `解释为何竞拍蔡文姬（第1次拍卖）`。通配参数使用对应的角色名称。不同生效条件可以使用同一组名，复核、场景及编辑均使用稳定组 ID。

AI 生成或刷新后，以同一正式事件、相同动作键参数及相同完整生效条件合并重复组。条件包含棋手、阵容范围，比较时识别等价的括号、组合顺序和键已经保证的事实。保留列表中的第一个组 ID，再合并人工改句、固定句、批注及来源。同文话术共用一个 ID，批注随之对齐。检查新加入的话术和变动后的优先级，实际内容改变时清除旧复核状态，以便复核最终可播结果。条件或参数确有差别时各自保留。
