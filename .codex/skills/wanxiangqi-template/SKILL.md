# 万象棋模板话术

玩家在当前盘面上为什么值得做这一步？先找能改变这个选择的事实，再决定在哪个正式事件上解释。用户指定解释类时使用「解释为何……」事件；提醒类按请求另行处理。

## 默认交付与资料入口

按[本地生成流程](references/generation.md)取得用户指定的输出文件名，获取并核对来源，再识别事件。先匹配[该事件已确认的骨架](references/event-angles.md)，再一次撰写 16 条不同候选，按各句最终质量收录全部达标句。已有库未命中时跳过；空库先提交草案，等用户确认。默认交付经本地求值的 v3 文件。定向生成优先按用户给出的知识和决策方向作答。全量自进化逐 case 接收整理好的知识与方向，26 题逐题交卷，详见[盲测规程](references/blind-evaluation.md)。

## 解释模板硬规则

- **禁止生造词。** 对所有事件逐句审查动词搭配、名词和缩写，使用自然中文和经核实的游戏术语。含生造词整句淘汰。

- 每条可独立播报的话术都必须把核心实体与至少一项能改变选择理由的事实联系起来，例如棋手、阵容、战场或手牌中的其他实体、对手、血量、等级或阿科米亚核心。条件要证明该事实实际成立，话术要说出它如何影响当前取舍。只点名、只写在说明里、只增加无关条件，都不能通过。任一可命中的条件分支都要满足这一要求。
- 禁止完整生效条件只识别某个事件参数的组。禁止只确认「选了 A」且候选列表包含同一个 A 的组。调换顺序、添加括号、使用等价运算符、使用单元素列表或限定普通与觉醒形态，都不能代替局面事实。
- 禁止只复述卡牌机制、合成或觉醒结果的组。用反例验证：只更换相关棋手、阵容或局面事实，仍然能照播且理由没有变化时，这句话尚未解释该局面的取舍。
- 购买、选择、拍卖英雄为一组，购买、选择、拍卖效果牌为另一组。每次从其中一个事件建组都要逐项评估同组另外两种场景，使用各自已确认的骨架。逐个记录可用事件、能核实的局面条件和独立收益。只在具备正式事件、充分条件和独立理由时建组；「拍卖开始」仅用于提醒。

## 从来源还原选择

刷新前读正式库与批注，按[反馈复盘](references/editorial-feedback.md)核对稳定组、原句和人工改稿。从组的来源反查笔记，同时从笔记全文（含举例、候选和获得途径）反查遗漏的选择。按[知识契约](../wanxiangqi-knowledge/references/knowledge-contract.md)读取正文、附件及条目证据；文字稿保留时间或原句。

### 1. 找出影响选择的收益

还原行动前的局面：玩家要解决什么问题？执行这个动作，谁获得什么，何时兑现，代价是什么？笔记只给做法时，联查行动者、作用目标及受益者的卡面和规则，核对形态、时点、数量、随机性及上限。多个效果同时存在时，比较它们对当前打法目标的贡献，优先讲能够解释此刻取舍的一个。

分别记录卡面直接证明的事实与结合盘面得出的策略推导。用户另行授权知识维护时，将能补充教学的原因和条件按[知识技能](../wanxiangqi-knowledge/SKILL.md)逐条绑定证据写回对应节点；沿用本批获得的写入授权。仅有待审核的新策略作依据时，先保留候选。

### 2. 沿同一收益寻找其他决策点

从收益倒推它需要哪些资源、角色和时机，沿实际获得途径往前看，也沿触发和保留收益的过程往后看。玩家已经有其中一端时，另一端的价值怎样改变？对每个可能的决策，重新确认行动前已具备什么、这一步改变什么、玩家还有什么选择。查[事件签名和参数](references/event-angles.md)落实到事件对象。候选池里的牌、选中的牌、原持有人、接收者等各有含义；一个事件成立的表达式不能照搬给另一个事件。上游选择能创造一次后续机会时，可以说这项机会；要说收益已经到手，还须能观察到中间动作已经完成。

### 3. 用替换和反例确定范围

先找出当前打法中改变这次选择的一项事实，分别替换来源方、受益方、对手、棋手、阵容或阶段。逐一核对放宽后每种对象的完整因果，同步调整组名、条件与正文。理由仍成立时寻找共同机制；替换后收益改变时，找出造成差异的事实。标签可表达一类效果，核对每种命中形态及提供者、受益者，确保整句都适用。一次效果含多段选人时，分别标明指定和随机的候选范围，比较候选只有一人和有多人时各段能否落到同一单位。观察不到的关键事实应缩小断言或留缺，记录会误播的具体局面。

按正式条件目录区分事件对象、己方、当前对手、最强对手和动作后的状态。阵容专属策略绑定棋手及阵容；验证过的通用机制可放宽范围。表达资源是否足够、目标能否选中、对局是否紧迫时查[实战条件与收益](references/game-decisions.md)。可观测前提进条件，保留随机结果的不确定性。

### 4. 按决策价值建组

玩家在此处学到了什么取舍？低频操作若有重要且可重复识别的收益，可以单列。若只有一次录像中的操作顺序、目标恰好是某张牌、或另一组合已能完整解释，就记录复用或舍弃的原因。双向核对材料与正式组时，按决策及证据定位，可记录无适用事件、缺条件或无独立教学收益。实体数量和事件数量均不作为配额。

先检查基础组适用时的主要理由，再问更具体的盘面多提供了什么信息。一次随机抽取的各句须服务同一目的；可以分别从当回合收益、解决的打法问题、可确认的后续收益来讲。每组一次生成 16 条，按本地生成流程选入全部合格句。个别句依赖额外事实时，另行检查是否有适用骨架和独立建组价值。

输出或更新模板组前，把以下五项写入「说明与依据-前置思考」（`explanation_before`）。记录原始内容并保留关键原句，详述该知识或技巧及收益，写出自然语言适用条件，将条件翻译为正式表达式，说明怎样在 30 字内讲清重点。考虑从取得关键要素的一端和兑现收益的另一端分别解释取舍，选出符合当前事件的一端。原「说明与依据」中的出处移入「说明与依据-来源」（`explanation_source`），只保留笔记条目、卡牌形态或文字稿时间等可复查的定位。源自 JSON「使用技巧」条目的同一技巧可以推导多个决策组，各组均加「技巧」标签。

### 5. 撰写并审核实际会播的句子

每组按[生成与筛选规程](references/generation.md)调用真实 Gemini 一次，请求 16 条不同候选和本组前置思考、来源。Codex 逐句核对首批原文，只选没有问题的话术。禁止生造词、手改、代写、返修和补句。整批无合格句则记录该组 0 句；含合格句则全部原样收录。缺少 Gemini 或生成失败时记录阻塞。明确维护旧组时仍保护既有固定句和身份。

结合[共用话术策略及已审批动宾词表](references/writing-strategy.md#按对象选词)核对这一步的实际收益和句子独立播报的质量，再逐句执行以下播报标准，并用本事件文档的案例库（盲测跳过案例）和[用词辨析](references/banned-terms.md)审读。推荐事件须交代推荐目标。

- 从必要对象或具体收益开始，说清效果如何发生、谁得到什么。保留必要的英雄、装备、卡牌及受益者全名。已知的购买、买下、上阵、使用、转移、刷新商店、结束回合、准备战斗等命令及同义命令均可省去。仅在多个操作容易混淆，或后续步骤、使用条件决定收益能否成立时说明动作。
- 用自然的主谓、动宾和清楚的并列关系。多个实体并列时交代位置关系，明确修饰语作用于哪些对象；跨句切换来源方与受益方时重申主语。普通同义词、合理省略和无害语气词可保留；普通连接词仅在多余或造成歧义时删去。
- 核对游戏内正式名词。商店、能量、英雄等级、法力值上限分别使用游戏内叫法，避免换成货架或卡池、金币或经济、星级、蓝量上限。按实际效果说「提升等级」「提高承伤能力」「恢复生命值」。从来源提取机制，再用玩家听得懂的话表达；避免照抄攻略文风、生造词、压缩词、夸张比喻及含糊的通用收益。
- 每句围绕一个主要因果，按兑现时机交代价值；确有两个独立理由时拆成两句，各句均须在命中局面成立。资源保留直接说「用于」哪个后续目标或「留作」什么用途。避免多层「便于」「有助于」「以便」、同义收益、目的堆叠和强行反转。
- 操作解释尽量控制在 30 个非空白字符内，槽位按实际展开，标点、数字、字母各计 1。先保留必要全名、当前用途、关键条件和因果，再删重复内容。仍超长时缩小到一个完整理由；不截断、不用简称或泛指藏起实际对象、不省略必要因果。

用完整候选池求值，分别检查应当命中、仅变动一个必要事实、关键值缺失、基础与细分组同时命中。核对优先级及实际可播的每一句。复盘批注后，另选未被点名的材料试提取：能否补出有据的理由、迁移到另一个有效选择，也能举出应舍弃的相似操作。按试提取暴露的问题修订判断标准。

点名能帮助玩家认出对象或听懂取舍时，可用 `{玩家.主C}`、`{对局.当前对手.主C}` 等目录中有名称的单实体路径，或显式引用其标量名称字段。播报取本局的名称，缺名时跳过该句。条件仍须证明所有可命中对象都满足整句所依据的机制和盘面，必要时用 `in` 限定候选。给直接槽位准备命中且有名称、命中但缺名的用例，并用可能出现的长名称验证 30 字上限。有限名单逐个核对，网页用 `/` 并列预览，动态槽位显示原始路径。

按每条随机候选句检查指代。辨认具体对象会改变玩家对收益的理解时，保留全名或使用名称槽位。身份可替换且共享同一机制时，可以用其共同职责；限定语须覆盖所有命中对象。

局面中的变化能说明当下取舍时，可以引用实际数字，例如剩余经验、合资格人数或全队等级。占位符保留被比较的数值路径或聚合式，如 `{玩家.升到下一级所需经验}`，生效条件必须在每次命中时都对该值做正向数值比较。数字的含义、单位和计算对象须与来源一致，数字应接在能解释提早行动或继续等待的理由上。比较阈值用于筛选局面，播报读实际值。网页和 v3 包保留数字占位符。给数字槽位准备临界命中、较长数字和缺值用例，按实际展开逐句核对可播效果与 30 字上限。

## 仅在用户另行要求时正式入库

- 从正式 GET /api/templates 读取组和话术 ID、fixed、人工修改与忽略状态。原用途沿用稳定身份，固定句连同 ID 原样保留。去重时核对忽略项，避免恢复人工排除的内容。
- 根据 docs/template-library.md 及当前接口使用 schema_version=3 的 speech-template-library 包。按正式名称配置 scope.player、scope.lineup 和 expression，核对导出的 effective_expression。包格式见 docs/examples/speech-template-library-minimal.json。运行 `scripts/check_batch.py 模板包.json`，动态名称或数字槽位同时传入 `--scenarios 用例.json`，并完成条件编译和实际求值检查。
- 用 /api/templates/import/preview 检查 changes、revision、preserved_fixed，再经 /api/templates/import/commit 提交。用户另行要求入库时默认产生待审提案。用户明确授权本批直写时，使用显式直写选项并记录原因，后续批次仍按默认流程。冲突时重读并预览。读回提案或正式库核对身份、固定句、忽略状态和实际差异，正式生效且回验后再关闭已解决的批注。仅要求生成文件时交付已核验的包。

## 本地交付和正式覆盖前逐组二次核验

生成或更新模板组后，默认模型按[二次复核清单](references/template-review-checklist.md)独立复核事件、条件和整组候选句。由默认模型根据实际复核与求值结果撰写「说明与依据-后置校验」（`explanation_after`），记录条件是否充分、话术的具体程度是否有条件支持、语法质量、冗余及尚待核实的事项。

初审先拆开每句候选所断言的事实，记录正式事件、行动时点、收益对象及对应卡面形态和来源。分别核对当前可实现的收益、满足条件后才可能取得的收益。声称能立即或连续操作时，核算此刻资源、每次消耗和每次结算；涉及阈值时核对计算对象、字段、比较方向及边界。仅当共同机制足以解释整句话时才推广到其他英雄；单一属性相似不足以证明同等收益。

复核从导出的生效条件、随机候选句全集和原始证据重新推导。逐句尝试构造「条件已命中，句子仍错误」的局面；改变英雄形态、目标、行动前后的状态、资源或阶段，检查替换后的理由。用正式求值器和同事件完整候选池分别验证应命中、临界值两侧、单项前提缺失、字段未知、多个组竞争。记录输入、实际命中和允许播出的句子；能编译或单个正例命中均不足以通过。未观测的前提若影响真值，收紧条件、拆句或退出匹配。

全量覆盖按旧组稳定 ID 对账。每组回查来源，逐句复核，重新写入三段说明和话术组。包中省略旧组仍会保留原记录，需删除时显式提交删除并读回核验。合格的固定句、人工改稿、忽略状态沿用。有保护项违反硬规则时按本批明确授权处理，固定句须先由管理员取消固定；没有解除授权时记录冲突并暂停匹配。新策略只有待审提案支持时留作候选。用未被批注点名的组检验新规则，正式库通过回验后再关闭已解决的批注。

全量复筛名称和数字槽位时，从正式库按稳定组 ID 逐组盘点 `in` 和数值比较，包括组合条件中的分支。逐项记录变量在这一事件中的对象、作用及读出来能帮助玩家做的判断，覆盖已经有槽位和仍用普通句的组。名单中的机制或收益有差异时分开验证。对只有阈值意义的条件保留现有说法。改稿逐句比较展开前后能否辨认动作、对象和收益，并记录采用或保留的理由。固定句、人工改稿和忽略项沿用上面的保护约定。

选择事件前，先按卡面区分「玩家指定目标」与「效果自行选取受益者」。群体、随机和按规则选人的效果都有受益者，事件签名仍取决于玩家是否指定目标。验收时补入场上没有任何合资格受益者的局面；只知道有人离场时，仅能断定其退出候选，宣称剩余收益归主力须另证候选范围。涉及一次性奖励时，将当前数值与历史领取状态分开。对主组、细分组和语义相邻的其他事件分别测试，连同组名、说明、候选句一起校对。

全量刷新采用 `scripts/check_scenarios.py 正式发布配置.json 用例.json --root 项目目录` 核验实际匹配与最终可播范围。配置取自 `/api/templates/published`。用例为数组，每项记录 `group: [正式事件名, 组名]`、`event`、`state`、`kind`（positive、negative 或 missing）、`matches` 以及局面理由 `reason`。预期命中但应被更具体的组覆盖时，设 `can_win: false`。槽位的可播用例添加 `expected_utterances`，按配置顺序列出该局面中每条候选展开后的文字。逐组保留正例、仅改变必要事实的反例、缺值情形及至少一例实际可播。针对语义复核发现的风险，先依据卡牌与游戏规则独立写出预期，再交给程序验证。
