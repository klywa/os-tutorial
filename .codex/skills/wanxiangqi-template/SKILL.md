# 万象棋模板话术

玩家为什么值得做这一步？先找这一步对棋手或阵容的通用收益，再找会改变选择的局面事实。用户指定解释类时使用「解释为何……」事件；提醒类按请求另行处理。

## 默认交付与资料入口

按[本地生成流程](references/generation.md)和 [正式注册表](../../../src/condition/catalog-v04.json)编写 v0.5 话术。先确定解释类型和额外信息键，再写条件。组保存为 schema 3 编审包，条件引用 `我方`、`对手`、`对局`、`动作`，话术引用 `{{表达式}}`。事件文档里的工作表原文与 `argN` 签名用于对照旧输入，编写时按注册表使用具名动作字段。

判断动作英雄是否属于当前阵容时，按事件字段使用 `动作.英雄.名称 in 我方.阵容英雄名列表` 或 `not in`。名单取自对局输入，缺失时保持未知。聚合谓词内使用 `.英雄阵容定位 != "非阵容英雄"` 判断当前元素。手牌等混合列表先加 `.卡牌类型 == "英雄"`。复核时覆盖成员、非成员和名单缺失三种局面。

按[本地生成流程](references/generation.md)取得用户指定的输出文件名，获取并核对来源，再识别事件。匹配[该事件已确认的骨架](references/event-angles.md)后先审条件，再用 Gemini 生成话术构思和 16 条候选，最多收录 6 条合格原句。已有库未命中时跳过；空库先提交草案，等用户确认。默认交付经本地求值的 v0.5 模板文件。定向生成优先按用户给出的知识和决策方向作答。全量自进化逐 case 接收整理好的知识与方向，26 题逐题交卷，详见[盲测规程](references/blind-evaluation.md)。

## 解释模板硬规则

- **条件禁止重复判断键已保证的事实。** 购买英雄的键为 `曹操` 时，禁止再写 `动作.选中.名称 == "曹操"`。结果已由具体键确定的反向等式、名单、否定和分支内比较也须移除。键为 `*` 时可用名单筛选。曹操是否觉醒、英雄等级、候选牌与阵容名单等额外事实仍可表达。迁移旧组时按表达式结构化简并检查分支。
- **阶段作用必须受条件约束。** 用 `对局.比赛阶段` 判断 `前期`、`中期`、`后期`，分界为第 3/4 和第 11/12 回合。用 `对局.当前阶段` 判断 `准备阶段`、`战斗阶段`、`拍卖阶段`。每条阶段断言都要在各可命中分支有依据，可使用比赛阶段枚举或有证据的回合边界。生成和复核都要用目标阶段、下一阶段和缺值验证。
- **逐句双向核对话术与条件。** 对每句、每个可命中分支，把话术中的对象、时机、收益和取舍映射到事件、额外信息键、范围及条件；再逐项移除或替换额外条件，确认它确实改变这句话的解释。通用出牌顺序不依赖现有库存。例如先上蔡文姬再打出三分英雄牌的顺序，本身无需场上或手里已有其他三分英雄；有库存的细分理由须讲清现有手牌如何让该收益更快兑现。必要事实表达不了时缩小断言、拆组或淘汰。

- **先说明为什么值得做，再定条件。** 写条件和话术前，从原文和卡面写出当前动作的收益。先写出两种局面。换成同样能获得该收益的对象，仍应适用。去掉真正必要的前提，这条理由应失效。涉及己方和对手时分别替换，保留作用相同的对象及不同的盘面身份。使用共同职责或属性建立通用组，只有具体英雄、阵容或赛季带来额外理由时才另建细分组。把事件及额外信息键已保证的事实作为起点，逐项删掉不影响取舍、受益者和兑现时机的条件，再用放宽后仍应命中的局面及缺少必要事实的反例验证。共享层同步处理。

- **泛化前必须逐赛季查完整卡牌库。** 先说明共同收益依赖哪项卡牌属性或机制，再查正式条件目录能否表达这项事实。对每个拟覆盖赛季，查完整卡牌库，逐项核对该机制可能涉及的所有对象及其属性、技能、触发方式和形态，记录卡牌库版本及纳入、排除的依据。例子、推荐名单和已有模板只作查找线索。共同字段能准确表达时优先用字段，即使有现成字段也要核对全库命中范围。语法表达不了时，用全库核实后的名单。完整卡牌库或关键属性缺失时记录缺口，该赛季的泛化仍待核实。

- **禁止生造词。** 对所有事件逐句审查动词搭配、名词和缩写，使用自然中文和经核实的游戏术语。含生造词整句淘汰。
- **棋手与阵容范围须有机制依据。** 保留范围时同时在知识依据和每条话术写明核心实体的实际职责、所依赖的机制以及它怎样改变本次选择。分别替换棋手和阵容，核对完整因果。理由依旧成立时，移除对应范围，必要时用能表达共同机制的局面条件。

- 每条可独立播报的话术都必须把核心实体与至少一项能改变选择理由的事实联系起来，例如棋手、阵容、战场或手牌中的其他实体、对手、血量、等级或阿科米亚核心。条件要证明该事实实际成立，话术要说出它如何影响当前取舍。只点名、只写在说明里、只增加无关条件，都不能通过。任一可命中的条件分支都要满足这一要求。
- 禁止完整生效条件只识别某个事件参数的组。禁止只确认「选了 A」且候选列表包含同一个 A 的组。调换顺序、添加括号、使用等价运算符、使用单元素列表或限定普通与觉醒形态，都不能代替局面事实。
- 禁止只复述卡牌机制、合成或觉醒结果的组。用反例验证：只更换相关棋手、阵容或局面事实，仍然能照播且理由没有变化时，这句话尚未解释该局面的取舍。
- 举一反三组内共享理由必须完全同步。英雄覆盖实际可取得的购买、选择、首拍和二拍。效果牌覆盖购买和选择，6 阶效果牌另覆盖第三次拍卖。装备覆盖穿戴、铸造和转移。通用组和每层细分组按实际可发生的入口逐层配齐，使用各事件正式字段和骨架，保持局面前提和条件具体程度一致。可发生的入口缺组或缺前提时暂缓该层。依赖动作独有机制的理由须有证据，可单独建组。刷新按[本地生成流程](references/generation.md#选择事件与骨架)复核成品。
- 条件中的阵营值使用正式全称：`三分之地`、`大河流域`、`逐鹿`、`河洛`、`日落海`、`建木`、`无阵营`。话术可用玩家熟悉的简称，例如「三分」「大河」。

## 从来源还原选择

刷新前读目标模板与批注，按[反馈复盘](references/editorial-feedback.md)核对稳定组、原句和人工改稿。用户指定来源范围时，从指定材料重新提取，旧组仅用于对账。按[知识契约](../wanxiangqi-knowledge/references/knowledge-contract.md)读取正文、附件及条目证据，文字稿保留时间或原句。

逐段登记笔记、表格相关单元格或文字稿的定位与结果。先列完整来源清单，再为每一段显式判断素材是否可用。逐条拆出行动及其独立收益，一段可有多条。每条素材逐项推导可能适用的正式事件，逐事件核对标准、写作策略和全部已确认骨架。按[覆盖记录](references/generation.md#逐段覆盖记录)保留建组、复用或跳过的证据，并在交付前核验整份清单。

### 1. 找出影响选择的收益

还原行动前的局面：玩家要解决什么问题？执行这个动作，谁获得什么，何时兑现，代价是什么？笔记只给做法时，联查行动者、作用目标及受益者的卡面和规则，核对形态、时点、数量、随机性及上限。多个效果同时存在时，比较它们对当前打法目标的贡献，优先讲能够解释此刻取舍的一个。

分别记录卡面直接证明的事实与结合盘面得出的策略推导。用户另行授权知识维护时，将能补充教学的原因和条件按[知识技能](../wanxiangqi-knowledge/SKILL.md)逐条绑定证据写回对应节点；沿用本批获得的写入授权。仅有待审核的新策略作依据时，先保留候选。

### 2. 沿同一收益寻找其他决策点

从收益倒推它需要哪些资源、角色和时机，沿实际获得途径往前看，也沿触发和保留收益的过程往后看。玩家已经有其中一端时，另一端的价值怎样改变？对每个可能的决策，重新确认行动前已具备什么、这一步改变什么、玩家还有什么选择。查[事件签名和参数](references/event-angles.md)落实到事件对象。候选池里的牌、选中的牌、原持有人、接收者等各有含义；一个事件成立的表达式不能照搬给另一个事件。上游选择能创造一次后续机会时，可以说这项机会；要说收益已经到手，还须能观察到中间动作已经完成。

### 3. 用替换和反例确定范围

先找出当前打法中改变这次选择的一项事实，分别替换来源方、受益方、对手、棋手、阵容或阶段。逐一核对放宽后每种对象的完整因果，同步调整组名、条件与正文。理由仍成立时寻找共同机制；替换后收益改变时，找出造成差异的事实。标签可表达一类效果，核对每种命中形态及提供者、受益者，确保整句都适用。一次效果含多段选人时，分别标明指定和随机的候选范围，比较候选只有一人和有多人时各段能否落到同一单位。观察不到的关键事实应缩小断言或留缺，记录会误播的具体局面。

按正式条件目录区分事件对象、己方、当前对手、全场其他玩家和动作后的状态。即使证据来自专门的棋手或阵容攻略，也要分别替换棋手和阵容，重查话术中的完整理由。理由仍成立时从 `scope` 和表达式移除对应限制，例如钟馗针对高等级单核。指出周瑜、吕布承接等级时，保留能证明受益者实际合资格的局面条件。逐句将每个具体因果的必要事实写入所有可命中分支，例如用奇才复制核心追觉醒，必须有合资格且明确未觉醒的核心。关键值缺失不匹配该细分理由。表达资源是否足够、目标能否选中、对局是否紧迫时查[实战条件与收益](references/game-decisions.md)。保留随机结果的不确定性。

### 4. 每个事件先通用后具体

1. 对本次涉及的每个正式事件，逐项查看该事件全部已确认骨架，按所需事实从少到多检查。先覆盖所有有来源支持、能作为独立理由的通用骨架，再考虑联动、阶段、对手和特殊技巧。判断通用程度看骨架前提。事件本身要求结果、目标或时机时，先保留这些必要事实。
2. 通用组使用正式动作对象和能解释收益的最少条件。英雄加阵容时，结合牌面效果、战斗技能及该英雄当阶段的实际战斗力解释职责。可说明后续获得配合牌时能兑现的收益，阵容职责组无需假设配合牌已上场或在手。阵容名只在帮助辨识选择时写进话术。骨架只要求装备和接受者时，用这两项解释适配。
3. 每加一个场上英雄、手牌、人数、等级、容错或对手条件，就把它从局面中移除或换成能满足同一机制的对象。理由仍成立就删掉限制或改用共同属性。理由发生变化时，只有新增事实可以观测、且能讲出通用组没有解释的独立取舍，才另建细分组。两组同时命中时，按实际能兑现的新增收益核验优先级。
4. 在工作稿按素材、事件、骨架编号记录覆盖结果。等价配合先枚举全部能产生同一收益的对象，用共同词条、职责或经过核实的完整名单建组，独有机制才点名另建。必需英雄始终先解释基础职责，细分组讲配合在当局增加了什么。交付前核对基础组实际存在，并验证移除配合条件后仍能匹配基础组。

一次随机抽取的各句须服务同一目的。每组一次生成 16 条。先选综合质量最佳的至多 3 条，再选与已选句有实质区别的至多 3 条。差异可以来自收益角度、因果重点或表达组织。同义替换、调换语序等不足以占补充名额。个别句依赖额外事实时，按上述顺序检查是否有适用骨架和独立建组价值。

输出或更新模板组前，把以下五项写入「说明与依据-前置思考」（`explanation_before`）。记录原始内容并保留关键原句，详述该知识或技巧及收益，写出自然语言适用条件，将条件翻译为正式表达式，说明怎样在 30 字内讲清重点。考虑从取得关键要素的一端和兑现收益的另一端分别解释取舍，选出符合当前事件的一端。原「说明与依据」中的出处移入「说明与依据-来源」（`explanation_source`），只保留笔记条目、卡牌形态或文字稿时间等可复查的定位。源自 JSON「使用技巧」条目的同一技巧可以推导多个决策组，各组均加「技巧」标签。

### 5. 撰写并审核实际会播的句子

条件定稿后，先用 Gemini API 生成「话术构思」(`wording_brief`)。构思供其他模型直接写话术，正文须包括五段：**生效条件**完整翻译范围、键、阈值、分支及排除项，**当前事件**复述动作和解释对象，**局面解释**给出已核对的事实、对象、机制、时机和因果，**写法与措辞**指出应写和应省的语义、组织方式及准确措辞，**建议话术**给出 1–2 条符合播报标准的示例。不得因字数省略必需信息，淘汰任何脱离当组仍可套用的指令。复核通过后，按[生成与筛选规程](references/generation.md)将构思原文和写作策略用于独立的 16 句请求。整批无合格句或生成失败时记录阻塞。

结合[共用话术策略及已审批动宾词表](references/writing-strategy.md#按对象选词)核对这一步的实际收益和句子独立播报的质量，再逐句执行以下播报标准，并用本事件文档的案例库（盲测跳过案例）和[用词辨析](references/banned-terms.md)审读。推荐事件须交代推荐目标。

- 从必要对象或具体收益开始，说清效果如何发生、谁得到什么。保留必要的英雄、装备、卡牌及受益者全名。已知的购买、买下、上阵、使用、转移、刷新商店、结束回合、准备战斗等命令及同义命令均可省去。仅在多个操作容易混淆，或后续步骤、使用条件决定收益能否成立时说明动作。
- 用自然的主谓、动宾和清楚的并列关系。多个实体并列时交代位置关系，明确修饰语作用于哪些对象；跨句切换来源方与受益方时重申主语。普通同义词、合理省略和无害语气词可保留；普通连接词仅在多余或造成歧义时删去。
- 核对游戏内正式名词。商店、能量、英雄等级、法力值上限分别使用游戏内叫法，避免换成货架或卡池、金币或经济、星级、蓝量上限。按实际效果说「提升等级」「提高承伤能力」「恢复生命值」。从来源提取机制，再用玩家听得懂的话表达；避免照抄攻略文风、生造词、压缩词、夸张比喻及含糊的通用收益。
- 每句围绕一个主要因果，按兑现时机交代价值。确有两个独立理由时拆成两句，各句均须在命中局面成立。收益的次数、数量、适用对象等上限在改变取舍或关系到断言真假时才进入播报。选择理由不依赖上限时，使用在全部命中局面成立的正面收益表述。资源保留直接说「用于」哪个后续目标或「留作」什么用途。避免多层「便于」「有助于」「以便」、同义收益、目的堆叠和强行反转。
- 操作解释尽量控制在 30 字内。每个 `{{表达式}}` 槽位计 4 字，正文的标点、数字、字母各计 1，空白不计。先保留必要全名、当前用途、关键条件和因果，再删重复内容。仍超长时缩小到一个完整理由；不截断、不用简称或泛指藏起实际对象、不省略必要因果。

用完整候选池求值，分别检查应当命中、仅变动一个必要事实、关键值缺失、基础与细分组同时命中。核对优先级及实际可播的每一句。复盘批注后，另选未被点名的材料试提取：能否补出有据的理由、迁移到另一个有效选择，也能举出应舍弃的相似操作。按试提取暴露的问题修订判断标准。

点名能帮助玩家认出对象或听懂取舍时，用 `{{我方.主C.名称}}`、`{{对手.主C.名称}}` 等显式名称路径。播报取本局的名称，缺名时跳过该句。条件仍须证明所有可命中对象都满足整句所依据的机制和盘面，必要时用 `in` 限定候选。给名称槽位准备命中且有名称、命中但缺名的用例，核对实际播报。有限名单逐个核对，网页显示动态槽位原始路径。

按每条随机候选句检查指代。辨认具体对象会改变玩家对收益的理解时，保留全名或使用名称槽位。身份可替换且共享同一机制时，可以用其共同职责；限定语须覆盖所有命中对象。

局面中的变化能说明当下取舍时，可以引用实际数字，例如剩余经验、合资格人数或全队等级。占位符写实际数值路径或聚合式，如 `{{我方.升到下一级所需经验}}`。数字的单位、含义和计算对象须与来源一致。比较阈值用于筛选局面，播报读实际值。给数字槽位准备临界命中、较长数值和缺值用例，核对实际播报。

## 仅在用户另行要求时正式入库

- 从正式 GET /api/templates 读取组和话术 ID、fixed、人工修改与忽略状态。原用途沿用稳定身份，固定句连同 ID 原样保留。去重时核对忽略项，避免恢复人工排除的内容。
- 用 `speech-template-library` 编审包（`schema_version=3`）。新组填写 `syntax_version: "0.5"`、`extra_key` 和 `expression`，话术对象带稳定 ID。按正式名称配置 `scope.player` 和 `scope.lineup`，核对派生的 `effective_expression`。运行 `scripts/check_batch.py 模板包.json`，动态名称或数字槽位同时传入 `--scenarios 用例.json`，并完成条件编译和实际求值检查。
- 用 /api/templates/import/preview 检查 changes、revision、preserved_fixed，再经 /api/templates/import/commit 提交。用户另行要求入库时默认产生待审提案。用户明确授权本批直写时，使用显式直写选项并记录原因，后续批次仍按默认流程。冲突时重读并预览。读回提案或正式库核对身份、固定句、忽略状态和实际差异，正式生效且回验后再关闭已解决的批注。仅要求生成文件时交付已核验的包。

## 本地交付和正式覆盖前逐组二次核验

生成或更新模板组后，默认模型按[二次复核清单](references/template-review-checklist.md)独立复核事件、条件和整组候选句。由默认模型根据实际复核与求值结果撰写「说明与依据-后置校验」（`explanation_after`），记录条件是否充分、话术的具体程度是否有条件支持、语法质量、冗余及尚待核实的事项。

初审先拆开每句候选所断言的事实，记录正式事件、行动时点、收益对象及对应卡面形态和来源。分别核对当前可实现的收益、满足条件后才可能取得的收益。声称能立即或连续操作时，核算此刻资源、每次消耗和每次结算；涉及阈值时核对计算对象、字段、比较方向及边界。仅当共同机制足以解释整句话时才推广到其他英雄；单一属性相似不足以证明同等收益。

复核从导出的生效条件、随机候选句全集和原始证据重新推导。逐句尝试构造「条件已命中，句子仍错误」的局面；改变英雄形态、目标、行动前后的状态、资源或阶段，检查替换后的理由。用正式求值器和同事件完整候选池分别验证应命中、临界值两侧、单项前提缺失、字段未知、多个组竞争。记录输入、实际命中和允许播出的句子；能编译或单个正例命中均不足以通过。未观测的前提若影响真值，收紧条件、拆句或退出匹配。

全量覆盖按旧组稳定 ID 对账。每组回查来源，逐句复核，重新写入三段说明和话术组。包中省略旧组仍会保留原记录，需删除时显式提交删除并读回核验。合格的固定句、人工改稿、忽略状态沿用。有保护项违反硬规则时按本批明确授权处理，固定句须先由管理员取消固定；没有解除授权时记录冲突并暂停匹配。新策略只有待审提案支持时留作候选。用未被批注点名的组检验新规则，正式库通过回验后再关闭已解决的批注。

全量复筛名称和数字槽位时，从正式库按稳定组 ID 逐组盘点 `in` 和数值比较，包括组合条件中的分支。逐项记录变量在这一事件中的对象、作用及读出来能帮助玩家做的判断，覆盖已经有槽位和仍用普通句的组。名单中的机制或收益有差异时分开验证。对只有阈值意义的条件保留现有说法。改稿逐句比较展开前后能否辨认动作、对象和收益，并记录采用或保留的理由。固定句、人工改稿和忽略项沿用上面的保护约定。

选择事件前，先按卡面区分「玩家指定目标」与「效果自行选取受益者」。群体、随机和按规则选人的效果都有受益者，事件签名仍取决于玩家是否指定目标。验收时补入场上没有任何合资格受益者的局面；只知道有人离场时，仅能断定其退出候选，宣称剩余收益归主力须另证候选范围。涉及一次性奖励时，将当前数值与历史领取状态分开。对主组、细分组和语义相邻的其他事件分别测试，连同组名、说明、候选句一起校对。

全量刷新采用 `scripts/check_scenarios.py 正式发布配置.json 用例.json --root 项目目录` 核验实际匹配与最终可播范围。配置取自 `/api/templates/published`。用例为数组，每项记录 `group: [正式事件名, 组名]`、`event`、`state`、`kind`（positive、negative 或 missing）、`matches` 以及局面理由 `reason`。预期命中但应被更具体的组覆盖时，设 `can_win: false`。槽位的可播用例添加 `expected_utterances`，按配置顺序列出该局面中每条候选展开后的文字。逐组保留正例、仅改变必要事实的反例、缺值情形及至少一例实际可播。针对语义复核发现的风险，先依据卡牌与游戏规则独立写出预期，再交给程序验证。
