# 事件与条件语法参考

模板组的 `utterances` 保存可供独立抽取的话术。组级 `version` 和 `mode` 用于版本、模式筛选，`tags` 为可同时筛选的标签列表。这些字段随组编辑、审批、导入和导出。旧包更新既有模板组时，省略这些字段会保留现值，显式传入空标签列表可清除标签。事件匹配由适用范围及条件表达式决定。

「说明与依据」分为前置思考（`explanation_before`）、来源（`explanation_source`）和后置校验（`explanation_after`）。旧字段 `explanation` 继续兼容读取，长度上限为 300 个 Unicode 码点。

### 在话术中引用条件值

如果条件含有 `玩家.主C in ["嬴政", "蒙犽", "孙膑"]`，且整条规则命中时这项判断必定成立，话术就可以写成「选穷兵黩武，{玩家.主C}施法能召唤玄雍士兵。」网页会显示「嬴政/蒙犽/孙膑」，播报会按当前局面只读出其中一个名字。编辑和导出保留原始占位符。

候选名称来自同一路径上的一条必选正向 `in` 字面量条件。仅在 `or` 的分支里出现、由 `not` 取反或右侧是动态列表的条件无法提供候选。同一路径出现多个必选候选列表时，先明确唯一来源再引用。命名实体字面量填入实体名称。装备穿戴事件中的 `{arg1}` 可引用符合这些条件的穿戴者。

数值路径、计数和求和也可用同样的花括号引用。条件必须在每次命中时都对该值做正向数值比较，使用 `<`、`<=`、`==`、`>=` 或 `>`。两个数值变量可以互相比较，`or` 的每个分支均有这种正向比较时也能引用同一个数值变量。由 `not` 取反的比较不提供绑定。实际值缺失时，比较结果为未知，按下文的组合规则求值。

例如，条件含 `玩家.升到下一级所需经验 <= 3` 时，话术可写为「还差{玩家.升到下一级所需经验}点经验就能升级。」当前需要 2 点时，播报填入 2。计数槽位可写成 `{玩家.战场.计数(标签, "登场")}`，单位由话术补上。网页对数字保留原始占位符，编辑和 v3 导出对所有槽位保留原写法。

发布前检查每句展开后至多 30 个 Unicode 字符，包含标点。候选名称逐个验证。数字用 `check_batch.py 模板包.json --scenarios 用例.json` 为每个数字槽位检查命中正例，并按这些用例中最长的数字文字计算展开长度。在正式运行配置上验证边界、缺值和实际可播文字。

一条规则先选定事件，再在该事件的参数作用域内写一个布尔表达式。事件参数描述动作发生时的对象或值；`玩家`、`商店`、`对局` 是动作完成后可查询的逻辑主体。点号沿属性取值，底层数据的存储和传递方式由接入方决定。

## 从一句需求写出条件

“刚上阵的英雄是当前主 C，主 C 至少 10 级，而且上阵后剩余能量不超过 3。”选定签名 `解释为何上阵英雄(arg1: 英雄)`，条件写成：

```text
玩家.主C.名称 is arg1.名称 and 玩家.主C.等级 >= 10 and 玩家.剩余能量 <= 3
```

假设上阵的是弈星，当前主 C 也是弈星、等级为 10，剩余能量为 3，结果为真。仅把主 C 等级改为 9，结果为假；仅让主 C 的等级未知，整条条件也不会命中。这里的 10 级来自当前主 C。若意图是“这次卖掉的是一名至少 10 级的英雄”，应选择 `解释为何从战场出售英雄(arg1: 英雄)`，写 `arg1.等级 >= 10`。即便英雄已离场，参数仍指向出售时的英雄。相同名称不会让不同路径共享动态属性。

## 事件声明与条件文法

### 棋手、当前打法与事件参数

“用百里玄策培养闪现英雄”绑定棋手「常小娥」和打法「常小娥灵活4人组-常小娥」，购买英雄事件的业务条件为 `arg1 is "百里玄策"`。卡片、编辑预览和「复制完整条件」都显示三项约束。

```text
玩家.使用棋手 is "常小娥" and 玩家.使用阵容 is "常小娥灵活4人组-常小娥" and (arg1 is "百里玄策")
```

v3 导出用 `scope.player`、`scope.lineup` 保存绑定名称，用 `expression` 保存业务条件，用只读的 `effective_expression` 提供完整表达式。修改绑定或业务条件后，导入会重算完整表达式。旧配置可以省略这个派生字段。匹配时先检查绑定和业务条件，再按优先级及同级业务条件的严格程度选择话术组。

「解释为何建议向某阵容发展」的 `arg1.阵容名` 指建议转向的目标。需要限制当前打法时，用模板的阵容绑定。

### 文法

以下 EBNF 用 `[ ]` 表示可选、`{ }` 表示重复、双引号表示实际字符。签名中的花括号、方括号等元符号不参与生成。

```ebnf
签名     = 事件名 "(" [ 参数 { "," 参数 } ] ")"
参数     = 参数键 ":" 类型
类型     = 基本型 | 命名型 | 联合型 | "Array<" 元素型 ">"
元素型   = 基本型 | 命名型 | 联合型
基本型   = "int" | "number" | "bool" | "string"
联合型   = 命名型 "|" 命名型 { "|" 命名型 }

条件     = 空文本 | 或式
或式     = 与式 { "or" 与式 }
与式     = 非式 { "and" 非式 }
非式     = "not" 非式 | 比较
比较     = 原子 [ 操作 原子 ]
原子     = 路径 | 字面量 | "(" 或式 ")"
路径     = 根 { "." 属性名 } [ ".求和(" 属性名 ")" | ".计数(" [ ("标签" | "阵营") "," 字符串 | "英雄" "," 英雄名单 ] ")" ]
英雄名单 = "[" (字符串 | 英雄字面量) { "," (字符串 | 英雄字面量) } "]"
筛选属性 = "标签" | "阵营"
根       = 本事件的参数键 | "玩家" | "商店" | "对局"
操作     = "is" | "in" | "has" | "<" | "<=" | "==" | ">=" | ">"
```

- **名称与作用域。** 事件名按目录中的完整名称选取。参数键匹配 `[a-z][a-z0-9_]{0,63}`，同一事件内唯一。保留词为 `and or not is in has true false`。属性名按主体目录逐级解析，`name` 可写作 `名称`，其余按原名书写。标识符和字符串值区分大小写。
- **数组求和。** `玩家.战场.求和(等级) > 20` 会累加场上英雄的等级，再与 20 比较。其他实体数组的求和属性须在所有候选元素类型上声明为数值。空数组的和为 0。数组或元素缺失，或参与求和的元素缺少该属性时，结果为未知。
- **数组计数。** `列表.计数()` 统计列表中的所有成员。英雄或单位列表可以按标签、阵营或英雄名单筛选，例如 `玩家.战场.计数(阵营, "三分之地") >= 3`。可视化树中先在「条件属性」选择相应的计数，再填写筛选值和比较值。
- **英雄名单。** `玩家.战场.计数(英雄, ["小乔", {"类型":"英雄","名称":"弈星","已觉醒":true}]) >= 2` 统计任意形态的小乔与觉醒后的弈星。每个符合条件的英雄单位各计一次，同名的两个单位计两次。非英雄单位跳过。空战场计 0。名单须非空。若缺少单位、名称或必要的觉醒状态，计数为未知。
- **字面量。** 布尔值写 `true` 或 `false`。数字使用十进制，可含负号、小数或指数。字符串用双引号，按 JSON 字符串规则转义。列表常量如 `["弈星","小乔"]`、`[1,2,3]`、`[]`，元素为字面量。命名实体常量如 `{"类型":"英雄","名称":"弈星"}`。这些是表达式里的常量写法。`未知` 是求值状态，没有对应的条件字面量。
- **组合。** 从高到低依次为括号、比较、`not`、`and`、`or`，连续的与或按从左到右组合。一个比较只接受一个操作符。闭区间写作 `玩家.血量 >= 10 and 玩家.血量 <= 30`。纯空白条件视作真；非空条件必须得出布尔结果。括号和取反合计最多嵌套 64 层。
- **签名示例。** `解释为何刷新商店()` 无参数。`解释为何选择英雄(arg1: Array<英雄>, arg2: 英雄)` 有两个参数。`Array<英雄|效果牌>` 表示各元素可来自这两种实体类型。类型须来自目录；联合型的各分支均为命名实体。

## 类型判断与操作

| 操作数 | 可用写法 | 判定 |
| --- | --- | --- |
| 两个数值 | `< <= == >= >` | 按数值比较，int 与 number 可互比。字符串 `"10"` 不会转成数字。 |
| 两个布尔值 | `==`；布尔表达式可用 `not and or` | `not arg1.已觉醒` 判断未觉醒。 |
| 字符串、名称、枚举 | `is`；也可作为 `in` 的左项 | 按值精确比较。属性可以和同类型属性比较。 |
| 命名实体 | `is` | 按类型和名称识别，同类型下名称唯一。单一实体类型可简写为名称，如英雄参数 `arg1 is "弈星"`。 |
| 单位 | `is`、`in`、`has` | 可用 `arg1 is "弈星"` 按名称比较，或用 `arg1 is {"类型":"英雄","名称":"弈星"}` 同时限定实际类型。列表成员也可以用名称或带类型的实体查找。 |
| 元素和列表 | `元素 in 列表`、`列表 has 元素` | 两种顺序含义相同，元素须与列表元素类型兼容，如 `arg1 in 玩家.手牌`。元素可以是数值、布尔、字符串或实体。 |
| 个别属性 | 以属性声明为准 | `装备.类型` 只允许 `is`。英雄伤害类型是封闭枚举，用常量比较必须取“物理”或“法术”；英雄定位允许扩展。 |

`商店.商店列表 has {"类型":"英雄","名称":"弈星"}` 查找英雄，遇到同名效果牌会区分类型。对于联合型参数，访问属性时该属性须在所有分支上存在且返回同一类型。例如 `card: 英雄|效果牌` 可读 `card.名称`；`card.等级` 无效。当前值恰好是英雄也不改变这条静态规则。

准备战斗时，`玩家.手牌 has {"类型":"棋手技能","名称":"小菟送福"} and 玩家.场上英雄数 < 4` 表示手中留有小菟送福且场上不足四名英雄。`玩家.人口上限` 是此时允许上阵的人数。两个整数由局面分别提供，均支持 `< <= == >= >`，缺失的字段按未知处理。

穿戴装备时，`arg1.已穿装备.计数() >= 2` 判断该英雄已穿至少两件装备。`arg1.已穿装备 has {"类型":"装备","名称":"装备名称"}` 判断指定装备是否已穿戴，`玩家.已选天赋 has {"类型":"天赋","名称":"天赋名称"}` 判断玩家此前是否选了指定天赋。将示例中的名称替换成要查找的卡牌名称。已知没有装备或天赋时传空列表。

推荐阵容时，事件参数 `arg1` 是建议发展的阵容对象。`阵容名` 是字符串列表，接入方将正式名称及所有已知别称放入同一列表。例如传入 `{"阵容名":["法师阵容","法师队"]}` 时，`arg1.阵容名 has "法师队"` 命中。成员按完整字符串匹配。写理由时结合本局已取得的英雄、装备、天赋、所用棋手，或已识别的对手与回合压力。

`玩家.当前阵容` 也可返回阵容对象，同样能继续取 `阵容名`。例如 `对局.当前对手.当前阵容.阵容名 has "法师队"` 检查对手的阵容。适用范围 `scope.lineup` 仍根据 `玩家.使用阵容` 的字符串筛选当前阵容。推荐其他方向时，可将适用阵容留空，在事件条件中指明建议的方向。

## 缺值、空列表与错误

属性合法但值缺失时得到“未知”。只有最终结果为真才命中。下表中 A、B 可交换，取反列只对 A 求值。

| A | B | A and B | A or B | not A |
| --- | --- | --- | --- | --- |
| 真 | 真 | 真 | 真 | 假 |
| 真 | 假 | 假 | 真 | 假 |
| 真 | 未知 | 未知 | 真 | 假 |
| 假 | 假 | 假 | 假 | 真 |
| 假 | 未知 | 假 | 未知 | 真 |
| 未知 | 未知 | 未知 | 未知 | 未知 |

空列表是一个已知值，成员判断为假。列表缺失时成员判断为未知。列表存在时，任一元素匹配就为真；没有匹配且至少一项无法确定则为未知。未声明字段、错误的操作数类型和语法错误应报告给作者。所有子表达式都须有效，`true or 玩家.未声明字段 > 0` 也会报错。

| 在“解释为何上阵英雄”事件中 | 结果或改写 |
| --- | --- |
| `arg1.等级` | 单独的数值不能作为条件，可写 `arg1.等级 >= 10`。 |
| `arg2.名称 is "弈星"` | 此事件只声明了 arg1。 |
| `arg1.名称 == "弈星"` | 字符串相等用 `arg1.名称 is "弈星"`。 |
| `10 <= arg1.等级 <= 30` | 拆成两个比较并用 `and` 连接。 |
| `not (arg1.已觉醒)` | 合法；缺少觉醒状态时仍为未知。 |

使用效果牌按是否指定目标选择对应事件。装备合成使用「解释为何铸造装备」，其参数依次为英雄、旧装备、新装备。

`单位` 可以接收英雄、衍生物和其他目标。接入方给衍生物传 `{"类型":"衍生物","名称":"衍生物名称"}`，给其他非英雄目标传 `{"类型":"单位","名称":"目标名称"}`。历史数据里的纯名称及没有类型标签的单位对象按英雄读取。购买事件的第二个参数是未选择的混合列表。“选择棋手技能”行中的“英雄技能”统一为棋手技能。末两项提醒的原表参数为空。

同类型参数的位置有业务含义。购买事件的 `arg1` 是买下的牌；所有“选择…”事件均以 `arg1` 表示候选列表、`arg2` 表示选中项。有目标的效果牌或棋手技能以 `arg1` 表示目标、`arg2` 表示使用的牌或技能。穿戴装备依次传英雄、装备；铸造装备依次传英雄、旧装备、新装备；转移装备依次传原持有英雄、被转移的装备、接收英雄。棋手升级传升级后的等级。发生与否由事件生产方判定，包括两条无参提醒。

| 单位 | `名称: string`、`已穿装备: Array<装备>`，英雄目标还可读取英雄属性，缺失时得到未知 |
| 装备 | `名称: string`、`类型: string` |
| 效果牌 | `名称: string`、`阶数: int` |
| 天赋 | `名称: string` |
| 棋手技能 | `名称: string` |
| 棋手 | `名称: string` |
| 衍生物 | `名称: string` |
| 实体 | `名称: string` |
| 商店 | `商店列表: Array<英雄\|效果牌>` |
| 对局 | `当前回合数: int`、`第一名玩家: 玩家`、`最强对手: 玩家`、`当前对手: 玩家` |

表中“抽象-列表型”“抽象-数值型”分别对应 Array 和 int，操作对同类型的中间结果同样适用。“抽象-英雄型”“抽象-玩家型”保留具体对象的所有字段，因此可以连续读取 `对局.当前对手.主C.等级`。英雄包括手牌和战场英雄。“觉醒进度”的原表类型 `tin` 按 `int`。定位、伤害类型、装备类型均按枚举名称比较。伤害类型限定为“物理”“法术”；装备类型为基础装备、普通装备、特殊装备、天赋装备。商店及手牌列表的元素类型是对原表 Array 的补充。


## 编写条件的验收方法

**同级命中时，优先采用条件更严格的组。** 如果 A 成立时 B 一定成立，而且存在 B 成立、A 不命中的情况，A 的命中范围就是 B 的真子集。两组同时命中时选 A。例如同为默认优先级 0，A 写 `玩家.剩余能量 <= 2`，B 写 `玩家.剩余能量 <= 3`。剩余 2 能量时选 A，剩余 3 能量时只有 B 命中。等价条件（如整数上的 `< 3` 和 `<= 2`）以及互不包含的条件保留同等机会。显式设置不同整数优先级时，较高者优先。判定比较的是条件表达式；事件和适用范围先用于筛选。

1. 选定一个已声明事件，逐个确认参数的角色、类型和顺序。例如“转移装备”中，原持有者与接收者都是英雄，须按位置区分。
2. 把每个判断写成“来源路径、操作、比较对象”。先判断需要动作当时的参数，还是动作完成后的主体属性，再选择路径。只组合目录中可表达的判断。例如“本局第一次购买”需要购买历史；现有目录没有这项属性，应记录缺少的数据能力。
3. 给规则配一个命中例、一个只改一项事实的未命中例、一个属性缺失例。对联合型，再配一个“名称相同、类型不同”的例子。用自然语言描述事实即可。

## 批注和审批

给整组提出意见可打开卡片上的「组批注与记录」；只需改一句时，从该句话术发起批注。所有编写员和管理员都能阅读并回复正式库的批注。全库批注入口默认显示待处理项，可定位到原组、原句。对象已删除时仍可核对批注时的原文。管理员处理后可以关闭，后续有新情况也可以重开。

卡片显示最近的管理员操作。在「管理员操作记录」中可查看时间、操作人、批次和修改内容。审批记录可对照原始提交稿、审批稿与正式结果。提案内的草稿和讨论只对提交者及管理员可见。

网页和技能的批量刷新都先生成差异，再提交提案。管理员在「提案审核」逐项勾选，或一次确认全部修改。只有用户明确要求当前批次直接入库时，管理员才使用跳过审批选项，并填写该次操作原因。
