对每个事件沿所附骨架逐项检查，从通用收益到阵容、棋手、场上英雄、手牌英雄、装备、天赋、对手、阶段、资源和必要组合。逐一移除前提，只有会改变理由且能观察的事实进入条件。区分已上场与仅在手牌。动作键识别解释对象，避免把选择事件已保证的事实充当局面依据。每种有效分支均须证明局面理由。使用 v0.5 正式字段和双引号字符串。编写正例、改变必要事实的反例、删除关键值的缺值例。组合有多个必要事实时分别删除或替换；负例与缺值例尽量保留同一动作，以验证局面条件。直接提供对局状态对象，包含动作、我方等根。不要填预测出的实际结果，程序会运行判定。例中字段须从该事件目录查取。可选 priority 为整数；以更具体的独立收益安排优先级。可选 version 为验证过的赛季数组。scope 为棋手/阵容绑定，阵容单独限制可直接写在表达式。每个事件给出有据且通过求值的条件；无可观测或有据条件时将该事件记入 rejected 数组，每项填写 event_id 和 reason。
缺少关键牌才成立的理由须同时检查手牌和场上等相关区域，并把每一区域分别改成已有卡的反例。有特定资源用途时，条件需核对实际限制，预期话术写出作用链，例如额外打出位怎样触发棋手技能。对策依赖爆发伤害时，从实际威胁选正式条件，不能仅凭阵容名推定。如果威胁不可观测，缩小断言或排除该组。升级理由区分当前等级能兑现的收益与之后的动作，只在有依据时解释无需停留及下一个需要操作的等级。
事件给出非空 base 时，至少提交一组 layer 为 base 的条件，其具体键和有效表达式合起来只使用 base.fields 列出的最小字段。细分组标为 refinement，优先级高于基础组，额外事实和收益另外写清。基础用例至少验证无额外事实时可命中，并用动作对象或必要条件的变化检验边界。模型负责提交表达式和用例，本地程序随后求值，模型没有工具权限不能作为排除理由。确需排除且事件无可表达的基础收益时，提供 blocker（missing_field、insufficient_evidence 或 duplicate_coverage）和 reference（明确缺失的正式字段、证据所对应的断言，或已覆盖的组），并填写 reason。
每项条件同时写 reason（为什么需要）、limited（实际限定的状态）、not_limited（条件没有保证的状态）、expected（具体说到什么程度）和 wording（措辞注意点）。这五项须紧扣该条件和事件，避免可套到任意组的套话。
先按事件注册表填写 `extra_key`，再写 `expression`。无参事件使用空键，多个参数按声明顺序用 `-` 连接，整段 `*` 表示通配。具体键「曹操」已经限定 `动作.选中.名称`，条件禁止重复使用等式、反向等式、等价列表及组合分支再次检查这项事实。条件可以判断动作对象的其他属性，例如觉醒状态，以及通配段上的名单。基础组的字段覆盖同时计算具体键与表达式。用 `对局.比赛阶段` 判断前期、中期、后期，用 `对局.当前阶段` 判断准备、战斗、拍卖阶段。
